# Guess the Music — roadmap / ideas

Phase 2 (all shipped):

- Resilience: fixed reconnect handling (host/tv/player now re-register on every Socket.IO 'connect', not just once) and persist player scores to players.json so a restart doesn't wipe them.
- Host UX: YouTube playlist import (Data API v3, needs YOUTUBE_API_KEY in .env — see README), drag-to-reorder playlist, optional round timer (soft cutoff).
- TV polish: buzz-in pop animation, confetti + chime on a correct answer, rotating idle-screen hints.
- Network robustness: mDNS hostname (guess-the-music.local) advertised as a secondary join hint; DHCP reservation is still a manual router step (see README).
- Ops: pm2-logrotate can't install on this machine (breaks on the space in the Windows profile path) — replaced with scripts/rotate-logs.ps1 + a daily scheduled task instead.

Also fixed two pre-existing bugs found along the way, unrelated to the above: `[hidden]` elements weren't actually hiding sitewide (CSS specificity — see style.css), and the YouTube IFrame API sometimes silently never initializes or starts playback (see tv.js's retry/backstop logic).

Phase 3 (shipped):

- Farsi/English toggle for the TV and player screens, set from the host page (EN/فارسی pill buttons) and broadcast live via state.language — no reload needed. Host control panel stays English-only by design. Translation dictionary + RTL/font handling lives in public/js/i18n.js; see that file to add more languages or strings.
- Delete player: host scoreboard has a remove button per player (host:removePlayer), which also reopens buzzing if it removes whoever currently holds the floor.

Phase 4 (shipped):

- Buzz sound + vibration on the player screen (Web Audio, no asset file; vibration is a no-op on iOS Safari).
- Song categories: optional freeform tag per song, filter-chip bar on the host playlist, host-only data (never sent to tv/player, so no hint leakage).
- End-of-game results screen: new 'results' roundStatus, 'Show results' button on host, ranked scores + one-shot confetti on TV, game-over message on player. 'Reset entire game' is the way back to idle.
- Wrong-answer feedback: resetBuzzers now targets a 'wrong' event (distinct tone + vibration pattern) at only the specific player's socket, not a broadcast.

Also fixed: tv.js's buzzed-panel, the correct-answer confetti gating, and player.js's "locked in"/"buzzed first" logic all used to key off `buzzOrder[0]` (the first buzzer of the round) instead of the current one — stale after a reset + a different second buzzer. All three now use `buzzOrder[buzzOrder.length - 1]`. Verified directly with a two-player buzz/reset/rebuzz sequence.

Phase 5 (shipped):

- Mobile drag-to-reorder: replaced the custom HTML5 drag-and-drop (mouse-only) with SortableJS (CDN), which covers mouse/touch/pen through one library. Handle-only drag (.grip), touch gets a short delay so scrolling through the handle isn't mistaken for a drag.
- Round auto-advance: opt-in "Auto-advance after reveal (sec, 0 = off)" on host. Server-side timer (state.autoAdvance, mirrors the round-timer pattern) auto-starts the next unplayed song after a reveal, cancelled by any manual round action in the meantime. Live countdown on host + TV.

Note for next time: on tv.html, anything that needs to be visible during the 'revealed' state must live outside `.overlay` (see the `#auto-advance-hint` element, moved there after first placing it inside `#panel-revealed` and finding it never rendered) — `.overlay` intentionally fades to invisible during 'revealed' to show the real video underneath.

Phase 6 (shipped):

- Playlist search: text box on the host page, filters by title/artist (case-insensitive substring), combined with the category filter rather than replacing it. Directly useful once the playlist has dozens of songs.
- Keyboard shortcuts for hosting from a laptop: Space = reveal, R = reset buzzers, C = close round. Reuses the existing button click handlers; guarded against firing while typing in an input; hint text hidden on touch devices.
- Home-screen app icon (PWA manifest) for host.html and player.html — "Add to Home Screen" installs a real app icon, opens full-screen, no re-typing the URL. Icon is a simple vinyl-record mark generated via an offscreen canvas (matches the TV screen's existing record animation), at public/icons/. Separate manifest per page (own name/start_url) sharing the same icon set.

Phase 7 (shipped):

- Custom logo: public/logo.svg, a vinyl record with a play triangle worked into the label (same visual language as the TV's existing record animation). Replaces the 🎵 emoji in every header and as the site favicon (SVG preferred, PNG fallback). PWA icons in public/icons/ regenerated from this exact SVG (drawn onto an offscreen canvas) so the header logo, favicon, and home-screen icon are all visually identical — previously the PNG icons had a plain center hole, predating this design.
- Pre-game readiness pass: confirmed pm2 healthy, reset playlist/scores to a clean unplayed state (a keyboard-shortcut test had marked one song played), and relaunched the actual kiosk window to confirm the full real deployment path (server + kiosk Chrome + autoplay flag) still works with every change applied.

Icon generation approach (reusable next time an icon changes): draw/load the design onto an offscreen `<canvas>` in a temp page under `public/`, `canvas.toDataURL('image/png')`, and POST it to a temporary `/_save-icon` Express route that writes the decoded buffer to disk — needed because the base64 data URL is too large to return through this session's tool output directly. Remove the temp route, temp HTML file, and any JSON body-size-limit bump afterward.

Phase 8 (shipped):

- Diagnosed "video unavailable": many official-label YouTube uploads have embedding disabled by the publisher — not fixable client-side. TV now relays its real YouTube player state/errors to the host (socket event, deliberately kept out of state/broadcast() since it's TV-local monitoring info, not shared game state) so the host sees "🔊 Playing" / "⏳ Buffering…" / "❌ Embedding disabled…" next to the round-status pill instead of guessing from silence.
- Playlist import now batch-checks embeddability via the YouTube Data API (videos?part=status, up to 50 ids/call) and drops unplayable entries before they can ruin a round; import status reports a skipped count. Manual single-song add gets the same check as a best-effort, non-blocking warning (only when YOUTUBE_API_KEY is set — manual add still works with zero API setup).
- TV visual polish: the record's ring texture was perfectly rotationally symmetric so spinning it showed no visible motion — added an asymmetric diagonal shine streak. Reveal title/artist render in a playful "Fredoka" font (Vazirmatn for Farsi, same RTL font-token override pattern as --font-display/--font-body). Generalized the old buzz-only entrance animation into a shared .panel-enter effect for every panel switch. Scoreboard entries pulse (scale + color flash) on both host and TV when a score changes.
- Host layout: "Add a song" card (manual add + import) collapses during a live round (playing/buzzed) to keep focus on the Current Round card and Scoreboard, reopens on idle/revealed/results.
- Explicitly out of scope: displaying song lyrics on screen was requested but refused — reproducing copyrighted lyrics to the audience isn't something to build regardless of source or implementation.

Phase 9 (shipped):

- The reveal panel's title/artist was fading with `.overlay` almost immediately (intentional, to show the real video underneath — see the Phase 5 note) — too quick to actually read. Added a persistent caption outside `.overlay` that stays up for the whole 'revealed' state.
- Broken-video cleanup: host can now scan the *existing* playlist (not just new imports) for videos that won't embed, and remove them one at a time or in bulk — `/api/check-playlist` reuses the same `checkEmbeddable()` helper from import-time filtering.
- Manual YouTube fallback for a playback error: a button pops the real youtube.com page in an ordinary Chrome window on the kiosk PC itself (the machine that's both running the server and HDMI'd to the TV), so a non-embeddable song can still be played manually. Server reads the video ID from its own state (never trusts the client) and validates it against YouTube's 11-char ID shape before it reaches `exec()`.
- More animations: buzz-in flashes the screen gold + a shockwave rings out from the buzzer's name on TV; idle screen has musical notes gently floating up; player's buzz button pops when it becomes pressable and shakes on a wrong answer, own score pulses on change; host's round-status pill flashes on any transition, new buzz-in rows slide in.
- Confirmed (again) that YouTube Premium has no effect on "embedding disabled" — that's a checkbox the video's owner sets, unrelated to the viewer's subscription. No legitimate workaround exists beyond avoiding/removing those videos or the manual fallback above.
- Confirmed no player-count cap exists anywhere in the code — join is a plain open dictionary keyed by generated player id.
- Lyrics-on-screen was requested again (reasoning: YouTube Music shows lyrics for most songs) and refused again — a lyric being *displayed* somewhere doesn't mean it's *licensed for redistribution*; YouTube Music licenses those specifically, this app doesn't. Not going to change.
- Incident: while cleaning up a test browser window opened by the YouTube-fallback feature, killed the wrong Chrome process via `Stop-Process -Force`, which disconnected the Claude Code browser automation extension (Chrome itself and the real kiosk TV window survived undamaged — confirmed via `Get-Process`). Lesson: don't `Stop-Process -Force` on a Chrome PID to close one window — closing a specific automation-opened window should go through the automation tooling itself, not raw OS process kill, since Chrome's PID-to-window mapping isn't reliably 1:1.

Phase 10 (shipped):

- Bug fix — "increasing one player's score bumps a different player's score": host.js's scoreboard re-sorted by score on every render, so the instant you tapped +1 the row could jump position; a quick second tap (natural when awarding several points fast) then landed on whichever player's row had just slid into that screen spot. Fix: the host's own scoreboard now stays in a stable (join) order and never reorders on score changes — it's a control panel being actively tapped, not a public leaderboard. TV/player boards are untouched and still rank live, since they're display-only (no click targets to misfire).
- Bigger, better-spaced touch targets on the host page for mobile: scoreboard +/- are now 2.75rem (3rem under 600px) round buttons, and the destructive remove-player button was made visibly smaller and moved further away (extra gap, wrapped the +/- pair in its own `.score-adjust` group) so a fast tap aimed at +/- can't land on it by mistake. Buzz-row award and playlist Play/Remove buttons got the same treatment. Both this and the scoreboard-order fix are pure static file changes (host.js/host.css) — express.static serves them straight from disk, so neither needed a pm2 restart to go live.

Phase 11 (shipped):

- Fixed a real auto-advance bug: `host:resetBuzzers` never cancelled a pending auto-advance timer, so firing it while 'revealed' (e.g. the `R` keyboard shortcut out of habit) left the countdown pill silently vanishing with nothing happening instead of visibly cancelling. Now clears it like every other manual round action.
- New **toggleable game options** system: `state.settings` (settings.json, mirrors the players/playlist persistence pattern exactly — `loadSettings()`/`saveSettings()`), a generic `host:updateSettings` socket event (patch object, only known boolean keys accepted), and a "Game options" card on host with one checkbox per feature. Broadcast to host/tv/player alike since later features need tv/player awareness too (e.g. blind mode). Settings not yet built render as visibly-disabled "(coming soon)" checkboxes so the list is self-documenting rather than appearing piecemeal.
- First feature shipped behind a toggle: **Steal Mechanic**. Reuses the existing resetBuzzers flow almost entirely (it already reopens buzzing to other players after a wrong answer — the wrong buzzer just can't re-buzz via the existing `buzzOrder` guard). When enabled, a `state.roundHadMiss` flag (set on resetBuzzers, cleared on `startRound()` and after one bonus is paid) drives a `+1` bonus in `host:awardPoint` plus a distinct `'steal'` TV event (STOLEN! banner + confetti/chime) instead of the normal `'correct'` event.
- Verification approach worth reusing: with a real session live and the browser extension still down from the Phase 9 incident, tested the whole steal-mechanic flow (16 checks: settings broadcast, full steal sequence, anti-double-bonus, and a regression check that the toggle OFF exactly reproduces prior behavior) against a **fully isolated second instance** of the server — copied `server.js` alone into a scratch dir with its own empty `playlist.json`/`players.json`, ran it on port 3999 via `NODE_PATH` pointing at the real `node_modules` (no need to copy/reinstall deps), drove it with a temporary `npm install --no-save socket.io-client` test script, then killed the test process and removed the temp dir + uninstalled the temp dependency. Zero risk to the live game/data — reuse this pattern for testing future features while a real session might be running.
- Backlog for the remaining toggle-gated features, in the agreed build order: speed bonus → point values per song → TV animation bundle (countdown ring, "takes the lead" banner, 3-2-1-GO flash, all under the `extraAnimations` toggle) → blind mode → session stats → karaoke-style blank-hint (copyright-safe lyrics alternative — no real lyric text) → team mode (biggest lift, deliberately last) → Spotify-based auto-categories (separate axis, needs its own `SPOTIFY_CLIENT_ID`/`SECRET` env vars, optional like `YOUTUBE_API_KEY`). Full plan for the first of these lives in the session history — re-derive similarly (short plan, one feature at a time) rather than trying to batch multiple.

Phase 12 (shipped) — the rest of the Phase 11 backlog, all one by one with a restart+commit between each:

- **Speed Bonus**: +1 for buzzing within 3s of `state.roundStartedAt` (set in `startRound()`), one-shot per round like the steal bonus (`state.speedBonusPaid`). Stacks independently with a steal bonus.
- **Point Values Per Song**: songs get an optional `points` field (default 1, editable inline in the host playlist row when the toggle's on); the Current Round card's award buttons auto-relabel to that value and just emit it as the delta — no server-side awardPoint changes needed, the bonus stacking already adds on top of whatever delta comes in.
- **TV animation bundle**: all under the existing `extraAnimations` toggle (confirmed: cosmetic-only additions share one switch, gameplay features each get their own) — countdown-critical pulse on the timer subtext in the last 5s, a "takes the lead" banner on sole (non-tied) 1st-place changes, and a "3...2...1...GO" flash on every new song start (tracked separately from `syncVideo`'s `loadedYoutubeId` so a replay flashes again too).
- **Blind Mode**: `payloadFor('tv')` swaps player scores to `null` (rendered as 🔒) until `roundStatus==='results'` — host and each player's own phone still see real scores always; sorting/lead-highlight/score-pulse all degrade safely on `null` with no extra guard code needed.
- **Session Stats**: new `stats.json` (same persistence pattern as players/playlist/settings), tracks two all-time records shown on the TV results screen — fastest buzz (a round's actual FIRST buzz only, not a post-steal one) and biggest single round award. Deliberately NOT reset by `host:resetGame` — it's a running record book across game nights, not a per-session stat.
- **Karaoke Hint**: no licensed lyrics source exists, so this masks the song's own TITLE instead (data the host already typed) — `buildHintMask()` on the server is the ONLY form of the title ever sent to TV while 'playing'; host has a "💡 Reveal a letter" button (`host:revealHintLetter`) that unmasks one random remaining letter at a time. Mask resets on every `startRound()`.
- **Team Mode**: optional "Team name" field always shown on the player join screen (harmless when unused, takes effect once the host flips the setting) — `player:buzz` blocks on ANY teammate already in `buzzOrder` (reuses the array as-is, so team locks survive a `resetBuzzers` the same way individual locks already did), and `host:awardPoint` fans the total award out to every player sharing the buzzer's team (steal/speed bonus eligibility still keys off the actual buzzer's own timing).
- **Auto-Categories**: mirrors the `YOUTUBE_API_KEY`-optional pattern exactly — needs its own `SPOTIFY_CLIENT_ID`/`SECRET` in `.env` (see README's new "Spotify auto-categories" section), works fine with neither configured. `suggestCategory()` does a cached client-credentials token fetch, searches the track, reads the first matched artist's genre. Hooked into both manual add (single lookup) and playlist import (concurrency-limited to 5 at a time). Never overrides a category the host typed themselves.
- Testing approach used for every one of these (from Phase 11's incident lesson — a real session was live throughout this whole batch, and the browser extension was still down): wrote a small Node test script per feature using a temporary `npm install --no-save --prefix <scratch-dir> socket.io-client`, against a fully isolated second server instance (`server.js` copied to a scratch dir with its own empty `playlist.json`/`players.json`, run on port 3999 via `NODE_PATH` pointing at the real `node_modules`), asserting real behavior end-to-end before ever touching the live server. Killed the test process and deleted the scratch dir after each one — zero risk to the live game or its data across all 8 features.

Phase 13 (shipped) — two more toggle-gated gameplay features, same one-at-a-time pattern as Phase 11/12:

- **Mystery Modifier Round**: exactly one song per game gets a random surprise twist, built entirely by reusing mechanics that already existed rather than inventing anything new — `double` overrides that song's runtime `points` value (the points-per-song pipeline does the rest, no new award logic), `noHint` forces the karaoke-hint mask off for that song regardless of the global toggle (plus a server-side guard on `host:revealHintLetter` so a stray client event can't bypass it), `blind` reuses blind-mode's exact score-hiding, just scoped to that one round instead of the whole session (hidden through playing/buzzed, back to normal the instant it hits 'revealed'). `ensureMysterySong()` picks lazily off the unplayed pool on every `broadcast()` and is sticky — once assigned it never re-rolls, even after that song's been played, so it's truly one song per game; `host:resetGame` is what clears it for a fresh pick next game. The modifier itself is withheld from every payload (host included) until the flagged song is actually the `currentSong` — so it's a genuine surprise, not just hidden from players. Host's playlist shows a 🎭 badge on the flagged song (which song, not what modifier) so they can choose when to play it.
- **Category Voting**: host starts a vote (`host:startCategoryVote`, categories auto-derived from unplayed songs, optional soft-cutoff timer mirroring the round-timer/auto-advance pattern) and players tap a category on their phone to vote, changeable until it closes; most votes wins, ties broken randomly, nobody-voted also falls back to random rather than getting the host stuck. Deliberately idle-only (rejected mid-round) so it never competes with an in-progress buzz round. Live tallies are visible everywhere (host/TV/players) rather than hidden until close — unlike the mystery round's suspense, watching votes come in live is the fun part here. TV swaps the vote UI in for the idle screen's join-QR block (same panel, not a new roundStatus) and reuses the exact same category strings the playlist already had; the host's existing category-filter chips are what "act" on the winner (`apply-vote-filter-btn` just sets the same `categoryFilter` variable `renderCategoryFilter` already reads).
- Testing approach: same isolated-second-instance pattern as Phase 11/12 (scratch dir, own empty `playlist.json`/`players.json`, `npm install` for both the server's own deps and `socket.io-client` since this scratch dir had no pre-existing `node_modules` to point `NODE_PATH` at this time — installed fresh instead). One script covering both features end-to-end, run 7 times in a row (modifier choice is random) to exercise all three mystery-modifier branches at least once each — all passed. Server killed and scratch dir deleted afterward.

Phase 14 (shipped) — first half of the "deploy off the PC" discussion: a real fix for non-embeddable videos, tackled before touching hosting at all since it's useful either way:

- **Find Replacement**: `findReplacement()` on the server searches YouTube (`search.list`, `videoCategoryId=10` to cut reaction/cover noise, `videoEmbeddable=true` as a cheap pre-filter) for a *different* upload of the same song — an "Artist - Topic" auto-upload or a lyric video often allows embedding when the official music video doesn't — then re-verifies the top candidates through the existing `checkEmbeddable()` helper (the search's own `videoEmbeddable` filter can be stale, same reasoning as everywhere else this app double-checks) and returns the first one that's actually embeddable. New `POST /api/find-replacement` route (`{id}` → `{replacement: {youtubeId, title, channelTitle} | null}`, reads the song's title/artist from server state rather than trusting the client) and `host:replaceSongVideo` socket event that swaps only the `youtubeId` — title/artist/category/points/played all stay exactly as the host had them, and the 11-char id shape is re-validated server-side rather than trusted from the client (same pattern as `host:openOnYoutube`).
- Wired into both places a broken video actually surfaces: the "🔁 Find replacement" button sits next to each row in the existing broken-video scanner (`/api/check-playlist`), and a matching button next to the live "❌ Embedding disabled" playback-error pill during an actual round — same shared `runFindReplacement()` render logic (found/apply/dismiss), just pointed at whichever song. A mid-round swap needs no separate "reload" event: broadcasting the new `youtubeId` on the still-`currentSong` is enough, since `tv.js`'s `syncVideo()` already reloads whenever `currentSong.youtubeId` differs from what's loaded — the exact same mechanism a normal next-song transition uses.
- Real cost worth knowing: ~100 quota units per lookup (a `search.list` call) against the free tier's 10,000/day default, so ~99 lookups/day — fine as a host-triggered per-song action, not something to run across a whole playlist at once. Documented in the README next to the existing YOUTUBE_API_KEY section.
- Testing approach: same isolated-second-instance pattern as Phase 11-13, but this was the first feature needing the *external* API mocked (no real `YOUTUBE_API_KEY` available to test with) rather than just Socket.IO — monkey-patched `global.fetch` in-process before `require('./server.js')`, passing through anything that wasn't a `googleapis.com` call to the real `fetch` so the test's own localhost requests still worked. First mock attempt gave a false failure: it simulated "not embeddable" by omitting an id from the `videos.list` response entirely, which instead tripped `checkEmbeddable()`'s deliberate fail-open behavior for an id the API didn't return at all (meant for a genuinely-missing video, not a blocked one) — fixed by having the mock return every id with an explicit `embeddable: true/false`, which is what the real API actually does. 11 checks covering the search→re-verify→pick-first-embeddable path, the swap, id-shape validation, the mid-round broadcast, and the no-key-configured error — all passing after the mock fix.

Phase 15 (shipped) — cartoon mascot + category avatars, plus a full app-wide regression pass ("make it rigid and reliable like Apple products"):

- **Cartoon mascot companion**: a face on the record (reuses `.record`'s exact gradient recipe at a smaller size, not a new asset) sitting in the TV's bottom-right corner, gated behind the existing `extraAnimations` toggle rather than a new one (cosmetic-only additions share one switch, per the Phase 12 convention). Five CSS-only expression states (`data-expression` attribute swapped by `updateMascot()`/`setMascotExpression()` in tv.js, all shapes done with eyes/mouth/cheek divs and border tricks — no hand-drawn SVG paths, matching the codebase's existing 100%-CSS visual style): idle bob, a surprised "buzz" pop, a cheering squint-eyed grin with blush on `correct`/`steal`, a frown-and-wobble on a wrong answer (inferred from the `buzzed → playing` transition via `resetBuzzers`, since there's no dedicated wrong-answer TV event), and a party hat for `results`. Lives outside `.overlay` like the other persistent TV elements, for the Phase 5 reveal-fade reason.
- **Category vote avatars**: new `public/js/avatars.js`, loaded cross-page exactly like `i18n.js` (plain global, no bundler). `categoryAvatar(name)` hashes the category string to a consistent pick from a curated music/party emoji set — same category always gets the same avatar, no host configuration needed, reliable across every browser (no custom-rendered art to get wrong). Wired into all three vote UIs (TV's badge-style rows, host's setup checkboxes/tally, player's vote buttons).
- Four real bugs found and fixed doing this (three via actually screenshotting the running app with Playwright/Chromium instead of trusting hand-written CSS coordinates, one via the full regression suite below):
  - Party hat was floating disconnected above the mascot's head with its pom-pom rendered nowhere near it — wrong coordinate math (didn't account for the CSS triangle trick's apex-vs-base orientation) plus wrong DOM paint order (hat needs to come *after* the head to layer on top of it). Fixed both; verified by cropping a zoomed screenshot of just `#mascot`.
  - The category vote panel clipped against the TV's scoreboard footer — the idle screen's spinning record + "waiting for next round" heading stayed visible above the vote list, leaving no room for it. Fixed by wrapping them in `#idle-waiting-block` and toggling the whole thing off during a vote (same swap idea `#idle-join-block` already used), instead of only hiding the join-QR block.
  - **The most important find**: `Sortable.create(...)` at the top of host.js ran unguarded at script-load time. When the SortableJS CDN script failed to load (happened in this sandbox; could just as easily be a flaky host WiFi or an ad-blocker in real use), the resulting exception silently killed every handler registered *after* it in the file — meaning the entire host control panel (playlist, scoreboard, settings, voting, everything) stopped responding to state updates, not just drag-to-reorder. Wrapped in `typeof Sortable !== 'undefined'`; reordering now degrades gracefully instead of taking the whole page down. This is exactly the kind of single point of failure worth hunting for under a "reliable like Apple products" bar — it had been there since Phase 5 and nothing had ever exercised it in an actual browser before.
  - The "3...2...1...GO" flash was replaying on every `host:resetBuzzers` (reopening buzzing after a wrong answer), not just on an actual new song — `lastPlayingSongId` was being cleared on *any* non-`'playing'` status, including the momentary `'buzzed'` state a reset passes through. Now only clears on `'idle'`/`'revealed'`/`'results'`, so a same-song reset doesn't look like a new round.
- **Full regression pass**: one ~460-line Socket.IO test script exercising essentially every socket event and feature toggle in server.js — registration, playlist CRUD (including reject-invalid-input cases), settings validation, language, the full steal/speed-bonus/point-values/karaoke-hint/blind-mode/team-mode stack together, session stats, round-timer soft-lock, auto-advance (including the Phase 11 resetBuzzers-cancels-it fix), removePlayer reopening a stuck buzz-in, mystery modifier round (all three branches + stickiness + resetGame reassignment), category voting (idle-only guard, live tallies, toggle-off clearing), a "toggles all off reproduces old behavior" regression check, reconnect handling, and malformed-payload survival — 76 checks, run clean 3 times in a row. Separately verified restart persistence end-to-end (kill the process, restart, confirm scores/playlist/settings/stats all reload from disk and every player correctly comes back `connected: false`, matching the Phase 2 design exactly).
- Debugging note worth keeping: most of the false starts writing that regression script were bugs in the *test*, not the app — `state.players` is an array (`publicPlayers()`), not an object keyed by id, so `state.players.p1` is silently `undefined`; `buzzOrder` is cumulative across a `resetBuzzers` within one round (by design, Phase 4), not cleared to `[]`; and `waitForState()` only resolves on a *future* broadcast, so checking the same already-past state transition on a second socket (e.g. host after already awaiting tv for the same round-start) can hang forever waiting for an event that will never re-fire — fixed by reading current state directly (re-register) instead of waiting for a new one wherever the value might already be settled.

Next ideas, not yet started:

- Resuming round progress after a restart (currently only scores persist — round state intentionally resets to idle).
- More languages — i18n.js's translations object is keyed by language code, so adding a third is mostly copying the 'en'/'fa' block and adding a toggle button in host.html.
- Remote play (join from outside the home WiFi) — would need a tunnel (Cloudflare Tunnel recommended) or Tailscale, plus a join PIN since the app currently has zero authentication (anyone with the link can join/control).
